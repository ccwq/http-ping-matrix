## Context

当前应用每秒采集网络延迟并持续追加日志。随着会话拉长，日志规模快速增长。现有路径里，日志表格与图表会在每次更新时对较大数据集执行映射、分组、排序与格式化，导致主线程计算和对象分配持续放大。虽然日志表格已使用虚拟列表，但其输入数据仍基于全量日志派生，无法从根本上控制长期会话下的渲染和 GC 压力。

## Goals / Non-Goals

**Goals:**
- 建立“会话窗口”作为统一数据边界，限制单次渲染和派生计算的数据规模。
- 日志表与图表共享同一窗口状态，避免各自独立全量扫描。
- 将热路径从“全量重建”调整为“增量更新 + 按窗口计算”。
- 在不改变核心监测语义的前提下，提升长时间运行稳定性。

**Non-Goals:**
- 不改变目标探测协议与采集语义（success/timeout/error 语义保持不变）。
- 不在本次变更中引入后端服务或云端存储。
- 不追求一次性解决所有可视化性能问题（例如复杂图形样式重构）。

## Decisions

1. 采用“会话窗口状态层”作为渲染数据源
- 决策：新增会话窗口状态（时间上界、窗口跨度、实时/历史模式、最大点数预算），由 composable 统一维护，表格和图表只消费窗口内数据。
- 理由：当前两个组件分别做全量派生，导致重复计算。统一状态层可减少重复与状态分叉。
- 备选方案：
  - 仅在组件内各自优化：改动分散，长期易回退到重复计算。
  - 仅缩短日志保留时间：可缓解但无法解决峰值抖动和会话期内突增。

2. 采用“增量缓存”替代“全量派生”
- 决策：对日志表的行映射和图表序列分组采用增量更新策略，仅处理新到达或窗口边界变化的数据。
- 理由：每 tick 全量 map/reduce/sort 是主要 GC 触发点。
- 备选方案：
  - 持续使用全量计算并增加节流：只能延后问题，无法改善单次计算峰值。

3. 建立“渲染预算”与降级策略
- 决策：定义窗口内最大记录数、每序列最大点数、更新节流频率；超预算时优先降采样与截断，保证交互帧率。
- 理由：海量数据场景下，稳定性优先于精细度。
- 备选方案：
  - 不设预算：在设备性能波动时不可控。

4. 数据持久化与渲染路径解耦
- 决策：持久化侧维持增量写入与按需读取，渲染层不依赖全量加载完成。
- 理由：避免“数据层慢”直接拖垮 UI 线程。
- 备选方案：
  - 仍全量读取后渲染：启动和长会话都不稳定。

## Risks / Trade-offs

- [风险] 窗口裁剪后，用户在极长时间回溯时可能看到分段加载延迟 → [缓解] 提供明确加载态与分批回填策略。
- [风险] 增量缓存逻辑复杂度上升，出现边界错误（重复点、缺点） → [缓解] 为窗口移动、暂停/恢复、清空日志建立可回放测试场景。
- [风险] 节流和降采样可能降低瞬时细节可见性 → [缓解] 提供可配置阈值，并在历史模式允许用户提升精度。
- [风险] 旧数据结构与新窗口模型并存期产生兼容问题 → [缓解] 明确迁移阶段和回退开关。

## Migration Plan

1. 引入会话窗口状态层与只读选择器，不改变现有 UI 行为。
2. 将日志表切换到窗口化数据源，验证渲染稳定性。
3. 将图表切换到窗口化分组数据，加入预算控制。
4. 调整存储访问模式为增量写入 + 按需读取，并验证导入/导出与清空行为。
5. 完成长时压测后移除旧全量派生路径。

回退策略：保留原全量路径特性开关，在性能或正确性异常时可快速切回。

## Open Questions

- 会话窗口的默认跨度与最大可调范围应如何设定，才能兼顾移动端与桌面端？
- 图表在超预算时优先“等间隔抽样”还是“保留峰值点”策略？
- 历史模式下跨窗口回放是否需要预取下一段数据以减少滑动卡顿？
